# 线程池耗尽告警处理方案

## 告警名称

- **告警名**: `ThreadPoolExhausted`
- **告警级别**: 严重
- **触发条件**: 活跃线程数接近最大线程数，队列长度持续增长，或任务拒绝数增加。

## 问题描述

线程池耗尽会导致请求排队、接口超时、异步任务堆积和级联故障。常见根因包括下游慢、数据库慢查询、线程池参数过小、任务阻塞、死锁和无限重试。

## 检索关键词

`ThreadPoolExhausted`、`RejectedExecutionException`、`queue_size`、`active_threads`、`blocked threads`、`thread dump`、`timeout`

## 排查步骤

### 步骤 1：查询应用日志

- 工具：`queryLogs`
- 日志主题：`application-logs`
- 查询条件示例：`RejectedExecutionException OR thread pool OR timeout`
- 重点字段：`pool_name`、`active_threads`、`queue_size`、`reject_count`、`trace_id`

### 步骤 2：查询慢接口和下游日志

- 工具：`queryLogs`
- 日志主题：`application-logs`
- 查询条件示例：`response_time > 3000 OR downstream timeout`
- 目标：确认线程是否被慢接口或下游依赖阻塞。

### 步骤 3：采集线程栈

- 查看线程状态是否大量处于 `WAITING`、`BLOCKED` 或网络读等待。
- 按线程名称聚合，定位具体业务线程池。

## 常见原因

### 原因 1：下游依赖响应慢

特征：

- 大量线程卡在 HTTP、RPC、Redis、MQ 或数据库调用。
- 线程池队列持续增长。
- 下游超时日志集中出现。

处理：

1. 缩短下游调用超时时间。
2. 开启熔断和降级。
3. 对调用方限流，避免线程全部阻塞。

### 原因 2：线程池参数不合理

特征：

- 核心线程数和最大线程数过小。
- 队列过长导致请求排队时间过高。
- 拒绝策略没有保护主链路。

处理：

1. 根据 QPS、平均耗时和 CPU 核数重新估算线程池大小。
2. 缩短队列长度，避免长时间排队。
3. 明确拒绝策略，优先保护核心请求。

### 原因 3：任务阻塞或死锁

特征：

- 线程栈中出现锁竞争。
- 少量任务长时间占用线程。
- 重启后短暂恢复，随后再次耗尽。

处理：

1. 分析 thread dump 中的锁等待。
2. 拆分长任务，避免同步等待。
3. 修复死锁或不合理的锁粒度。

## 应急处理

1. 对非核心入口限流。
2. 临时扩容应用实例。
3. 缩短下游调用超时并启用降级。
4. 必要时重启被阻塞实例，但要保留线程栈。

## 验证方式

1. 活跃线程数回落。
2. 队列长度下降。
3. 拒绝任务数不再增长。
4. 接口 P99 和错误率恢复。
