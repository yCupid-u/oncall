# 下游依赖超时告警处理方案

## 告警名称

- **告警名**: `DownstreamDependencyTimeout`
- **告警级别**: 严重
- **触发条件**: 下游 HTTP、RPC、Redis、MQ 或数据库调用超时率持续升高。

## 问题描述

下游依赖超时会拖慢调用方线程池，导致接口 P99 升高、错误率升高和线程池耗尽。排障时要确认是单个下游异常、网络问题、调用方超时设置不合理，还是依赖自身容量不足。

## 检索关键词

`DownstreamDependencyTimeout`、`timeout`、`connection refused`、`circuit breaker`、`fallback`、`Redis timeout`、`MQ timeout`、`RPC timeout`

## 排查步骤

### 步骤 1：查询调用方日志

- 工具：`queryLogs`
- 日志主题：`application-logs`
- 查询条件示例：`downstream timeout OR connection refused OR circuit open`
- 重点字段：`dependency_name`、`api`、`timeout_ms`、`retry_count`、`trace_id`

### 步骤 2：确认影响范围

判断：

- 是否只有一个服务受影响。
- 是否只有一个下游依赖异常。
- 是否跨实例、跨可用区或跨地域出现。

### 步骤 3：检查重试和超时配置

重点查看：

- 是否存在无上限重试。
- 超时时间是否大于接口整体 SLA。
- 重试是否放大下游压力。

## 常见原因

### 原因 1：下游服务容量不足

特征：

- 下游响应时间升高。
- 多个调用方同时超时。
- 下游 CPU、线程池或连接池接近上限。

处理：

1. 通知下游服务扩容。
2. 调用方启用限流和熔断。
3. 降低非核心调用频率。

### 原因 2：网络或连接异常

特征：

- 日志出现 `connection refused`、`reset`、`no route`。
- 超时集中在某个可用区或实例。
- 依赖服务本身指标可能正常。

处理：

1. 切换到健康实例或备用地址。
2. 检查服务发现、DNS 和负载均衡配置。
3. 摘除异常实例。

### 原因 3：调用方重试放大故障

特征：

- 单次失败触发多次重试。
- 下游压力被重试流量放大。
- 调用方线程池被重试任务占满。

处理：

1. 限制最大重试次数。
2. 增加指数退避和随机抖动。
3. 对非幂等接口禁止自动重试。

## 应急处理

1. 开启熔断和 fallback。
2. 对非核心功能降级。
3. 缩短调用超时，避免线程长期阻塞。
4. 如果有备用依赖，切换备用路径。

## 验证方式

1. 下游超时率下降。
2. 调用方 P99 恢复。
3. 线程池队列和活跃线程数回落。
4. 熔断恢复后无再次抖动。
