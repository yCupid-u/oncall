# 数据库慢查询告警处理方案

## 告警名称

- **告警名**: `DatabaseSlowQuery`
- **告警级别**: 严重
- **触发条件**: 慢查询数量持续增加，或单条 SQL 执行时间超过 1 秒并影响核心接口。

## 问题描述

数据库慢查询会导致接口响应时间升高、连接池耗尽、CPU 使用率上升和请求排队。排障时必须先确认慢 SQL 是否与当前告警时间窗口一致，再判断是索引缺失、执行计划异常、锁等待、数据量增长还是连接池配置问题。

## 检索关键词

`DatabaseSlowQuery`、`slow query`、`query_time`、`rows_examined`、`connection pool`、`lock wait`、`EXPLAIN`、`index missing`

## 排查步骤

### 步骤 1：确认慢查询时间窗口

- 工具：`getCurrentDateTime`
- 目标：确定告警发生时间，后续查询日志时使用同一时间窗口。

### 步骤 2：查询慢 SQL 日志

- 工具：`queryLogs`
- 日志主题：`database-slow-query`
- 查询条件示例：`query_time > 1000 OR rows_examined > 10000`
- 重点字段：`sql`、`query_time`、`rows_examined`、`db_name`、`table_name`、`trace_id`

### 步骤 3：关联应用日志

- 工具：`queryLogs`
- 日志主题：`application-logs`
- 查询条件示例：`timeout OR SQLTimeoutException OR connection pool exhausted`
- 目标：确认慢 SQL 是否导致 API 超时、线程阻塞或连接池耗尽。

### 步骤 4：分析执行计划

- 对慢 SQL 执行 `EXPLAIN`。
- 检查是否出现全表扫描、索引未命中、临时表、文件排序或扫描行数异常。

## 常见原因

### 原因 1：索引缺失或索引失效

特征：

- `rows_examined` 很高。
- 查询条件字段没有合适索引。
- 使用函数、隐式类型转换或前置通配符导致索引失效。

处理：

1. 为高频过滤字段、排序字段或 join 字段补充索引。
2. 避免在索引字段上使用函数或隐式转换。
3. 用 `EXPLAIN` 对比优化前后的扫描行数。

### 原因 2：锁等待或事务过长

特征：

- 慢 SQL 时间集中在更新、删除或热点行操作。
- 日志中出现 `lock wait timeout`。
- 事务长时间未提交。

处理：

1. 查询当前锁等待和长事务。
2. 终止异常长事务前先确认业务影响。
3. 优化事务范围，避免在事务内做远程调用或大批量处理。

### 原因 3：连接池耗尽

特征：

- 应用日志出现 `connection pool exhausted`。
- 慢查询数量上升后，接口开始排队或超时。
- 数据库本身 CPU 不一定最高，但应用线程被阻塞。

处理：

1. 临时扩容应用实例或连接池上限。
2. 限制慢接口流量，避免连接池被打满。
3. 优先修复慢 SQL，而不是单纯扩大连接池。

## 应急处理

1. 对影响核心接口的慢 SQL 做限流或临时降级。
2. 对明显缺失索引的查询补充临时索引。
3. 对异常长事务或锁等待进行人工确认后处理。
4. 如果由新版本引入，优先回滚到稳定版本。

## 验证方式

1. 慢查询数量下降。
2. P99 响应时间恢复。
3. 数据库连接池使用率回落。
4. 应用日志不再出现 SQL 超时或连接池耗尽。
